## 一、项目定位

| 项 | 内容 |
|----|------|
| 一句话 | 以《山海经》原文为纲的白描图赞连载，一兽一期，可逐字复核 |
| 平台 | 小红书图文（竖版 3:4） |
| 差异化 | **可核验的考据**：卷次 + 原文 + 注，且**可数特征必须数对** |
| 不做什么 | 不做"AI 还原山海经"式的奇观堆砌；不做无出处的演绎；不让模型写字 |

**为什么必须靠考据**：这个题材在 AI 绘画里极度饱和，用户已经看过上千张九尾狐。视觉本身不再是稀缺资源，**"能被核对"才是**。

## 三、制版工艺

### 已定工艺（R6–R8 修正、猼訑期补引擎后）

```
① 出图      默认 Z-Image-Turbo（快、但负向通道为空、几乎必盖印）；
            特征与"模型已知的概念"冲突时换 Qwen-Image（慢、有真负向、不带盖印先验）   ✅ 猼訑期建立
② 制版      typeset_zanzhi.py：榜题 + 原文 + 卷次 + 边框            ✅ 已实现（5 项排版自检；印章待字库）
③ 核数      目视点数并留档（放大裁图存档；corner_sheet.py --box 出特征图）—— 读作九条即可，**不作机械确证**
④ 滤印      四角 12% / 6× 放大目视（seal_check.py 只报疑、**不能报安**）→ 有印则 patch_region.py
            擦除（自检 + 与未擦除版逐像素核对）并留档                        ✅ 鹿蜀期建立
⑤ 评分      A–F 六维（F 气韵 .25），`fatal` 仅用于硬伤
```

### 写法规则（鹿蜀 R1–R5 / 九尾狐 R7–R9 实测，二期起照此写）

| 规则 | 证据 |
|------|------|
| 英文点名 + **特征逐项** | 鹿蜀 v5 写法（`pure white head` / `bold black tiger stripes` / `only its long tail is cinnabar red`）四项全中 |
| **不要用中文直述** | 中文组两轮 6/6 失败：虎纹丢成斑点、毛色偏褐、赭石过饱和 |
| **"不要画什么"没有用** | R3 三种 no-seal 写法 **9 张全无效** |
| **"改写先验"也抑不住印** | R5/R9 四种骨法句（换媒介名词 / 画面占满 / 换素白纸 / 底座对照）× 3 seed × 2 件 = **24 张全部有印** → 抑印只剩"多出几张挑干净的"（约 1/20）与"工具擦除"两条 |
| **"更浓"要付系列一致的账** | `bold` 虎纹 / 更浓的尾巴画得出来（A 满分），但墨色与对比一起上来：虎纹候选加权 4.38 < 定稿 4.60、狐候选 4.63 < 定稿 4.80；要浓就得把骨法句的纸色/墨色一起调暗，并让两件同轮重跑 |
| **点名式不是万能钥匙** | 猼訑（模型不认识的兽名 + 九尾羊）：Z-Image 上 R1+R2 共 **21 张 0 中**；而九尾狐 8/8、鹿蜀四项全中 —— 差别在"该特征与模型已知的概念相容不相容"。写法强度要匹配这个距离（猼訑期建立） |
| **计数塞进名词短语 > 介词短语** | `nine-tailed, four-eared bo-yi` 让尾巴从 1 条变 2–3 条（Z-Image 上唯一有反应的一式）；`a sheep with nine tails` 仍是单尾 |
| **不成立就换引擎** | 同一段 prompt：Z-Image 0/21 → Qwen-Image 一次成立。两引擎差异不止画风（真负向 / 盖印先验），见 §三 ① |
| **补色要付形变代价** | 加 `soft ochre / warm brown` 后 6 张里 4 张跑成**狼** → 补色必须多出几张、逐张验形；Qwen 上骨法句要"STYLE 逐字保留 + 追加一句显式设色" |
| 赤色要显式限定部位 | `only its long tail is …` 才压掉模型自作主张的红鬃 |

> ⚠️ **本工艺相对初版有重大修正**：初版把"锁死可数特征"当成第一道工序，投入了程序化控制图 + Canny +
> ControlNet 一整套装置。R6–R8 实测证明**这套装置是在给一个不存在的问题造机器**——真正决定成败的是
> **prompt 的写法**。详见 [rounds/r05-review.md](subjects/jiu-wei-hu/rounds/r05-review.md)。

### 探针实测结论（2026-10-05）

| 验证点 | 结果 | 证据 |
|--------|------|------|
| 白描骨法成立 | ✅ | v3 样张：匀细墨线、留白充足、中式语汇正确 |
| 木刻质感成立 | ✅ | v1/v2 样张：刀刻排线清晰、做旧纸底（封面用） |
| 风格跨 seed 稳定 | ✅ | R1 六种子扫描，六张语言高度一致 |
| **可数特征可控** | ❌ | **六张全部没数对**：prompt 明写 `EXACTLY nine tails`，实得 7–9 条且边界重叠，2 倍放大后仍无法可靠点数 |
| 模型不擅自加料 | ❌ | 要求 monochrome 却在耳上加橙色；v2 出现**乱码印章**与多余红点 |

**两条铁律由此而来**：
1. **字不由模型写** —— 榜题、原文、印章一律工具叠真字（模型画的印章是乱码，属硬伤）
2. **数不由模型保** —— 可数特征必须走结构控制或人工复核，不能赌 prompt

### ❌ 已废弃：程序化结构控制图（R6–R8 证伪其必要性）

> **本节保留为教训记录，不再作为工艺环节。**
> 初版假定"prompt 控不住计数"，于是用几何构造图 + ControlNet 强行锁死。实测走下来：
> 每修一个"假"就冒出下一个"假"（细带→空心线稿；尖叶→叶脉感；加厚→花瓣；去机械化→仍像扇骨），
> 而**同期的纯文生图只要把 prompt 改成点名写法，就 4/4、8/8 出九尾且明显更好看**。
> 真正的病根是 prompt 写错了（描述式 + `EXACTLY nine` + `no hatching`），不是模型不行。

九尾狐的可数特征是**九尾**，初版据此采用了路线 B：把计数从「赌模型」改成「由几何构造保证」。

```bash
python3 scripts/control_image.py --creature jiu-wei-hu --width 864 \
  --out work/shanhai-jing/jiu-wei-hu/r02/control-nine-tails.png
# → tail_count: 9（构造保证） / min_gap_px: 31.52 / border_ink_px: 0 → OK
```

`scripts/control_image.py` 带两项**自证**（退出码 0 才算通过）：

| 自检 | 判据 | 实测 |
|------|------|------|
| 分离自检 | 超出 `disentangle_r`（0.20）后九条尾巴两两分离，最小间隙 > 0 | ✅ 31.52 px |
| 构图自检 | 外侧 7px 环带内墨迹像素 = 0（避免出图被裁切） | ✅ 0 px |

管线：`control_image.py` → Canny → ControlNet（`comfyui_edit.py`）→ 白描成品。
控制图是**确定性**的（同参数重跑逐像素相同，`pngdiff` 实测 `SAME`），因此"九尾"这件事在整条链路上可复现、可审计。

> 已弃用：**A 大样本筛选**（扫 40–60 张目视点数）。理由是证据强度不足——放大后尾巴边界仍模糊，"数对了"永远只是主观判断，撑不起"严格考据"的招牌。

### 印章：篆体字库（⏸ 未解决，阻塞中）

要求：开源可商用（OFL 类）**且覆盖印文所需汉字**。这个"且"是踩出来的——

| 候选 | 许可 | 实测 | 结论 |
|------|------|------|------|
| [lxgw/LxgwSeal](https://github.com/lxgw/LxgwSeal) | SIL OFL 1.1 | **仅 375 个码位**：「九」有，「尾」「狐」缺（渲染成替代方块） | ❌ **不可用**（基本只覆盖 Unicode 小篆区） |
| [SuperMate-Ai/JFZSKSealScript](https://github.com/SuperMate-Ai/JFZSKSealScript) V3.5 | SIL OFL 1.1 | 2.4 MB；release CDN 302 后超时 | ⏸ 待换源重试 |

**引入任何字库前必须先跑覆盖检查**：

```bash
python3 scripts/font_coverage.py --font F.ttf --text 九尾狐
# → 缺字会逐字列出，缺字则 exit 1
```

这道闸门是必要的：肉眼在一张图里**分不清「篆书」和「缺字方块」**——最初的渲染测试就是这么骗过眼睛的。

现状：**印章层暂缺**，不阻塞画心、榜题与原文。**绝不接受模型生成的乱码印**（探针 v2 已实测出乱码印）。

## 五、验收标准

### 评分维度（满分 5，加权）

| 维度 | 权重 | 判据 |
|------|------|------|
| **A 考据准确** | .25 | 原文逐字对、卷次对；**可数特征逐一点数相符**；形态描述逐项落地 |
| **F 气韵生动** | .25 | 毛体质感、线条有笔意与疏密、姿态自然、构图有呼吸；**不是一张空心线稿** |
| **B 骨法纯正** | .15 | 是本件骨法（**现为赭石设色工笔淡彩**；R7 前为白描墨线）；未跑成水墨晕染 / 国潮厚涂 / 西式版画排线，也没有明显的铅笔排线阴影 |
| **C 制式完整** | .15 | 留白充足、构图端正、有榜题位与边框，合图赞制式 |
| **D 辨识度** | .10 | 一眼读出是哪个异兽，不与其他条目混淆 |
| **E 系列一致** | .10 | 与同批成品同一套线条密度、纸底、留白 |

> ⚠️ **F 维度是补上的**。初版评分表只有 A–E 五个"正确性/一致性"维度，**没有一项衡量美感**。
> 后果是实测出来的：程序化控制图 + 高强度控制 + 「uniform thin weight / no hatching」的 prompt，
> 产出了一张**数得对但最难看**的图，却在旧表上拿了 4.65 分、被判「首选成品」。
> 教训：**验收表缺哪一维，就会在哪一维上系统性退化**——不是运气差，是评分表把选型推到了那个解。

### 门槛（硬性）

- **`fatal` 非空 → 不合格**。`fatal` 包含：**明显计数错误**（如只有一条尾、明显不是九）、原文错字、卷次错、出现乱码印章、模型生成汉字
  - 「出现乱码印章 / 模型生成汉字」的**可执行判据**（鹿蜀期建立）：每张候选四角裁 12% 短边 / 6× 放大目视（`scripts/corner_sheet.py` 固定版面出图并自检，可 `--enhance levels|redness`）；
    `seal_check.py` 只负责机械筛出候选（四种自动定性判据实测全失败，见 `subjects/lu-shu/rounds/r01-review.md` §四）
     - ⛔ **机械筛不能反用**：被判 `CLEAN` 的 5 张（鹿蜀 3 + 九尾狐 2）目视全都有印（R5/R9 实测）——它只能"报疑"，不能"报安"
    确需保留该图则用 `patch_region.py` 擦除并在 `manifest.json` 记 `seal_erasure`（自检：残留 ≤5%、接缝 ≤30；**外加与未擦除版逐像素核对，差异必须全部落在补丁框内**）
- `A < 3`、**`F < 3`** 或 `C < 3` → 不合格（画得难看同样不能交付）
- 总分 ≥ 4.0 且 `A ≥ 4` 且 `F ≥ 4` → 首选成品；≥ 3.5 → 成品；其余为备选（**不纳入成品**）

### 计数复核流程

1. 出图后**裁可数特征区域**并放大（`ffmpeg crop+scale`，存档到 `work/`）
2. **目视点数并把过程写进** `rounds/rNN-review.md`
3. **只有「明显错」才判 `fatal`**（一条尾、明显五条…）；蓬松兽尾尾羽交叠时，"读作九条"即通过
4. 判据标注为**「目视点数，非机械确证」**

> ⚠️ **不要恢复成机械确证门槛**。实测教训：把"可机械确证恰好 9 条"当硬门槛，
> 会逼出几何构造的、机械的图（R2–R5），而毛茸茸的兽尾本来就无法用游标卡尺量。
> 判据的强度要匹配对象的性质。详见 [rounds/r05-review.md](subjects/jiu-wei-hu/rounds/r05-review.md)。

### 底座对照

每轮必带**同轮底座对照**（`period-NN/controls/`），沿 [bio-splice](../bio-splice/README.md) 的做法。
